# Release Notes — v1.7.0

**Дата**: 2026-05-23
**Тема**: Stakeholder-driven Operational Tier + PMO-constraints as single source of truth

---

## Что изменилось и зачем

### Проблема, которую решает этот релиз

До v1.7.0 система собирала бизнес-идею, но не собирала операционные ожидания стейкхолдера:
- Пользователь не указывал хотел ли он мониторинг, автовосстановление, алерты
- s1-pm принимал решения об Operational Tier на предположениях
- Эти решения не доходили до s4-devops — каждый агент начинал с нуля

v1.7.0 закрывает этот разрыв через три механизма:

---

## Ключевые изменения

### 1. s0-kickoff: 5 блоков, 26 вопросов (было 4 блока, 19)

**Новый Блок 3** собирает операционные ожидания на бизнес-языке:
- Как развернуть приложение? (один контейнер / несколько / облако)
- Что ожидаете при сбое? (само перезапустится / уведомление / отчёт о сбое)
- Нужен ли мониторинг? (нет / базовый / полный дашборд)
- Есть ли существующая инфраструктура мониторинга?
- Что нужно от команды? (только код / код + docker / полный деплой)

**Блок 1 переориентирован** на проблему: сначала боль пользователя, потом продукт.

**Блок 5 "Неизвестное"**: known unknowns и потенциальные стопперы — первый класс рисков.

---

### 2. s1-pm: Operational Tier Selection (Tier 0–3)

На основе ответов стейкхолдера s1-pm выбирает тир надёжности и объясняет его на бизнес-языке:

| Тир | Что получает пользователь | Для кого |
|-----|--------------------------|----------|
| **0 — Minimal** | restart при сбое, логи через docker logs | внутренний инструмент, best-effort |
| **1 — Basic** | + /health endpoint, JSON-логи, алерт на падение | небольшой продакшн |
| **2 — Standard** | + метрики, дашборд, SLO-алерты, runbook | B2C продакшн с SLA |
| **3 — Full** | + circuit breaker, DLQ, watchdog, postmortem | критичный SaaS, финансы |

Матрица автоматически обнаруживает **противоречия** — например: «полный мониторинг + только код» — и выносит на уточнение до начала работы.

---

### 3. Veto Protocol — стейкхолдер управляет сессией

В интерактивном режиме пользователь получает контроль над каждой секцией Feasibility Study:
- Презентация плана до начала работы
- Чекпоинт после каждой секции: подтвердить / пропустить / изменить / остановить
- При пропуске секции — ВЕРДИКТ адаптируется, предупреждение о неполноте анализа

---

### 4. Handoff → PMO-constraints → все downstream агенты

s1-pm теперь заканчивает Feasibility Study структурированным YAML-блоком `## → Handoff`.
s1-pmo читает этот блок и записывает `tracking/PMO-constraints.md`.

Этот файл читается ПЕРВЫМ в каждом downstream агенте:
- **s2-ba** → переводит `inherited_nfr` в BA-NFR.md с числовыми порогами
- **s3-arch** → учитывает `architectural_constraints` при проектировании HLD
- **s3-security** → помечает риски из `critical_risks` как `[PMO-RISK-N]`
- **s4-devops** → реализует согласно `infrastructure_constraints` и Operational Tier

---

### 5. Исправлены 9 нарушений изоляции агентов

Handoff-ключи именовались через имена агентов (`nfr_for_s2ba`, `constraints_for_s3arch`) — это нарушало принцип изоляции: s1-pm знал о существовании других агентов.

Переименовано на семантические, agent-agnostic ключи:
- `nfr_for_s2ba` → `inherited_nfr`
- `constraints_for_s3arch` → `architectural_constraints`
- `constraints_for_s4devops` → `infrastructure_constraints`

---

## Совместимость

- **Существующие проекты**: обновление не ломает существующие артефакты. `tracking/PMO-constraints.md` добавляется при следующем запуске s1-pmo.
- **idea.md**: старые файлы без новых полей (Recovery Expectation, Monitoring Expectation и др.) — s1-pm выдаст DoR-violation, предложит запустить `s0-kickoff /refresh → Block 3`.
- **Handoff YAML**: переименование ключей не обратно совместимо. При наличии уже записанных `PM-feasibility.md` с Handoff — s1-pmo прочитает файл, новые ключи появятся в PMO-constraints.md при следующей записи.

---

## Миграция для существующих проектов

```bash
# 1. Добавить недостающие поля в idea.md
cd _agents/s0-kickoff
claude "/refresh my-project"
# → выбрать "Block 3 — Технические ограничения"

# 2. Обновить Feasibility Study (опционально)
cd _agents/s1-pm
claude "/feasibility my-project"

# 3. Создать PMO-constraints.md
cd _agents/s1-pmo
claude "/charter my-project"   # читает PM-feasibility → Handoff, создаёт PMO-constraints.md
```
